# 解析モデルと現在の境界

## データの流れ

```text
 exported source ────────────────┐
                                 v
 .xlsm → ZIP → CFB → MS-OVBA → source decoding
                                 v
                     conditional preprocessor
                           lexer / parser
                                 v
           declaration and name indexes / call candidates
                                 v
         structural CFG / Excel and host-operation candidates
                                 v
                    JSON or Graphviz DOT
```

入力ファイルの記述を実行する機能はありません。`.xlsm`処理はコンテナの読み取りとソース抽出を行い、`vbaProject.bin`内のモジュールソースを解析器へ渡します。

## 意味の状態

- 構文上確認できるもの: 宣言、プロシージャ、パラメーター、構造文、文字列・数値リテラル、行位置。
- 型の推定: 組み込み型と宣言型を使った基本的な代入式の型伝播。暗黙変換、Variant、Office型は候補状態。
- 解決できる場合があるもの: 同一・別モジュールのプロシージャ名。名前が一致しても、VBAの完全な名前解決やオーバーロード・既定メンバー解決を意味しません。
- 候補: Excelオブジェクトモデルの読み書き、Shell・COM・ファイル関連操作、外部/ホスト呼出。
- ホスト依存知識はVBAコアから分離し、`.xlsm`入力ではExcel、エクスポート済みコードでは既定でホスト不明として扱う。
- 未解決: ライブラリ参照、暗黙のVariant、遅延バインド、Officeホストの型や既定プロパティ、コンパイル条件。
- 未検証: 入力値で実行可能な経路かどうか、Excelが実際に行う効果、p-codeとソースの一致。

解析に未対応の構文を確認したときは、黙って完全扱いせず、診断または未解決状態を残します。ただし診断網羅性もまだ完全ではないため、診断がないことは正しさの証明ではありません。

## 次の精度向上

1. MS-VBAL全体を対象にした構文適合性と静的意味規則の拡張。
2. 宣言スコープ、型、定数、引数、既定メンバーを含む完全な名前・型解決。
3. 条件コンパイル式の全構文とOfficeホスト定数の対応。
4. 代入・引数・戻り値・Excelセル間のデータフロー。
5. 例外状態と`On Error`を含む制御フロー。
6. 手元で利用許諾を確認したOfficeバージョン別データを使う抽出・相互運用試験。
7. p-codeの根拠ある命令セット資料が確立した場合に限る、別層でのコンパイル済み表現の分析。

現時点では`compiled::inspect_vba7_line_map`が、利用者が選択した観測プロファイルに対して`CA FE`シグネチャ、行数、12バイト行ディレクトリ、各行の生バイト範囲を検証します。命令語やオペランドの意味は解釈しません。

項目7は現在のキャッシュ指紋機能を逆アセンブラと呼び替えて実装済みにするものではありません。Microsoftの形式仕様では性能キャッシュはバージョン依存で、読み込み時に無視する領域として定義されています。p-code命令の解釈には、別途、対象バージョンと検証資料が必要です。
